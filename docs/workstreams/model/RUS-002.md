# RUS-002 — рельеф в матрицы precompute

Адресат: агент Руслана. Сначала прочитать `docs/architecture/OPTIMIZER_CORE.md`.

## Правила этого брифа

- Ветка от `main`. Контракт `v0`.
- Секреты, токены, адреса машин и URL с учётными данными не коммитить.
- Чужой шов не трогать: `geometry`, MILP, метаэвристика, `routes_raw`, `route_builder`, `validator`, внешний перебор Миши, API и хранилище заданий.
- Дедлайн показа: 25 сентября 2026, 21:00 Europe/Moscow.
- После показа код сшивает отдельная задача. Этот бриф сшивку не делает.

## Goal

Снять плоское приближение. Читать рельеф из отдельного KML местности и учитывать его в матрицах времени и энергии `precompute`. Ключи словаря `pre` остаются прежними.

Это осознанное исключение из правила «бекенд не пишет оптимизацию». На этот чекпоинт разрешён только шов рельефа в `precompute`. API, очередь, SQLite и солверы в задачу не входят.

## Inputs and assumptions

- Шов этого брифа — `optimizer/precompute.py`.
- KML местности — только группа `terrain` из протокола: `kml_path`, `crs`, `horizontal_unit`, `elevation_unit`. В `optimizer/models.py` добавляется только эта группа. Группу `zone_constraints` не добавлять и существующие поля `InputData` не переименовывать.
- KML ограничений полётной зоны (`zone_constraints.kml_path`) не читать и не подменять им файл рельефа.
- CRS и единицы берутся из полей группы. `elevation_unit` — `metre`. Молча подставлять WGS84 или метры нельзя. Пустая CRS или пустая единица — недопустимый вход шва.
- Высота рельефа меняет длины и перепады, из которых считаются время и энергия. Имена ключей `t`, `e`, `tau`, `eps`, `T_takeoff`, `T_landing`, `E_takeoff`, `E_landing`, `T_max`, `E_max` сохраняются. Время — секунды, энергия — Вт·ч.
- Плоский фикстур без группы `terrain` (`data/input.json`) остаётся регрессией: матрицы считаются как сегодня, по сфере и постоянной высоте полёта.
- В одном вызове остаются одинаковые борта, один вылет, постоянный ветер и один GSD.

## Deliverables

1. Чтение `terrain.kml_path` внутри `precompute` и учёт рельефа в матрицах времени и энергии.
2. Файл `data/terrain.kml` и тест, который сравнивает плоский и рельефный прогон на одних и тех же полосах.
3. Регрессия плоского `data/input.json` без группы `terrain`.
4. Строка статуса в `docs/status/backend.md` со ссылкой на этот бриф.

## Acceptance criteria

- При заданном `terrain` матрицы `t` и `e` отличаются от плоского счёта там, где рельеф меняет путь, и по-прежнему выражены в секундах и Вт·ч.
- Набор ключей `pre` совпадает с протоколом.
- KML зоны не открывается.
- `data/input.json` без `terrain` даёт прежний плоский расчёт.
- Солверы, `geometry`, API и `solver.solve` не изменены.
- Метаэвристический результат не называется глобальным оптимумом.

## Explicitly out of scope

- Чтение KML полётной зоны и правки построения полос.
- Правки MILP, метаэвристики, `route_builder`, `validator`, контракта `routes_raw`.
- Эндпоинты, воркер, SQLite, фейковый движок, VPS.
- Перебор площадок и типов БВС.
- Сшивка нескольких вызовов ядра.

## Dependencies and consumers

- Полосы приходят из шва Гриши уже построенными. Этот бриф их не перестраивает.
- Оба солвера читают те же ключи `pre`.
- Миша передаёт путь KML местности в вызов и сам файл не парсит.
- Исключение узкое: файлы вне списка `allowed_paths` не редактировать. В `models.py` — только группа `terrain`.

## Risks / decisions required

- Формула, как метры рельефа входят в `t` и `e`, записывается рядом с расчётом и не выдаётся за снятие постоянного ветра или одного GSD.
- Общую геометрию зоны с Гришей этот бриф не сливает. Сшивка — отдельная задача после показа.
