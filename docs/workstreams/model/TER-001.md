## Promoted expert decisions

### EXPERT-QA — terrain and altitude

- WGS84 may be used for this hackathon task. TER-001 still requires the CRS to be declared explicitly, for example `EPSG:4326`; it must not be silently inferred.
- Survey altitude is height above ground level (AGL), not a fixed absolute altitude.
- Useful survey flight maintains the required height above the terrain surface.
- Low-level tracking of the terrain-relative altitude profile may be assumed to be handled by the UAV autopilot. TER-001 plans the profile; it does not implement flight-controller behavior.
- Terrain may be supplied from GeoTIFF data or an elevation service, and the planner may assume terrain information is available.
- The optimizer must not query terrain every metre. Approximately 20–30 m sampling is sufficient for planning.
- Complex battery and vertical-energy physics is not required for the MVP. A linear/passport-duration simplification is acceptable.

The central survey relation is:

```text
z_required(s) = z_terrain(s) + h_AGL
```

All terms are metres. The absolute-altitude datum remains explicit in the provider/configuration and must not be invented by the implementation.

### LATEST-EXPERT-CLARIFICATION — fleet

- Users select UAVs only from profiles embedded in the system.
- No external live fleet-management integration is required.

### LATEST-EXPERT-CLARIFICATION — battery

- Passport flight duration is an acceptable autonomy baseline.
- The landing reserve is approximately 5–10%.
- In strong wind, an approximately 10% safety reserve/margin is acceptable.
- Earlier Q&A used an illustrative 20% battery cutoff. The later clarification supersedes that demo expectation; TER-001 must not use 20% as the current default.

### LATEST-EXPERT-CLARIFICATION — sensor and survey speed

- Detailed sensor/survey-speed restrictions are not required now.
- The architecture may add them later.
- TER-001 must not grow into a sensor-physics model.

### TEAM-DECISION — implementation policy

- Default terrain sampling step: `25 m`, the midpoint of the expert-recommended 20–30 m interval. It is configurable and strictly positive.
- Default landing reserve for terrain-aware policy: `0.10`, the conservative end of the later expert 5–10% range. It is configurable.
- Inputs that do not opt into the new terrain/autonomy policy must retain the current flat-model behavior for the v0 regression. Applying the new reserve to all legacy inputs requires a separately reviewed migration decision.
- Missing or non-finite elevation fails closed with a useful model error. It must never silently become zero elevation.
- Deterministic synthetic/in-memory providers are the required test mechanism. No test may use the network.
- GeoTIFF and elevation-service support are adapters around the provider abstraction. TER-001 must not add a heavy GIS dependency or live service call unless separately approved after dependency review.
- No dedicated climb-power aerodynamic model is introduced. Terrain may affect existing budgets through changed three-dimensional distance, time, and the current energy formula.

### OPEN — not resolved by expert statements

- The absolute elevation datum and any conversion between source datums.
- A production GeoTIFF adapter/library choice and interpolation method for real rasters.
- Transfer clearance when no explicit clearance input exists.
- A numerical definition of “strong wind”; TER-001 must not invent a hidden threshold or double-count the existing wind term.
- A public v0 scenario representation for terrain inputs. This is a proposed contract change, not part of TER-001 implementation authority.
- Certified flight safety, autopilot tracking tolerances, and obstacle-clearance certification.

## Goal and repository-native architecture

The canonical optimizer flow remains:

```text
geometry -> precompute -> MILP or metaheuristic
         -> routes_raw -> route_builder -> validator
```

TER-001 adds a deterministic terrain abstraction in `optimizer/terrain.py`, conceptually:

```python
class TerrainProvider(Protocol):
    def elevation_m(self, lon_deg: float, lat_deg: float) -> float: ...
```

Naming may follow repository conventions, but units and CRS must remain explicit. Required test implementations include flat and synthetic/in-memory terrain. Core model code must not perform network requests.

`precompute.py` remains the integration seam. It samples survey strips and transfer legs at the configured interval, builds the required AGL profile for survey samples, and feeds terrain-aware three-dimensional distance/time/energy into the existing solver-facing matrices. Both solvers must continue consuming the existing keys:

```text
t, e, tau, eps, T_takeoff, T_landing,
E_takeoff, E_landing, T_max, E_max
```

The complete `pre` key set and `routes_raw` meaning must not be renamed or silently changed. MILP and metaheuristic code are outside the allowed paths.

The current wind model—a constant vector with `speed_ms` and `direction_deg`—remains authoritative. TER-001 does not add a weather API, altitude-dependent wind, time-dependent forecasts, or a new meteorological subsystem.

The active UAV model has `max_flight_time_s`, `battery_wh`, and `v_vertical_ms`, but no maximum-altitude field. Therefore max-altitude infeasibility is required only if an approved base adds an explicit maximum-altitude value before TER-001 starts. Manufacturer limits must not be invented.

## Terrain is not obstacles or restricted airspace

- **Terrain** is the ground elevation surface handled by TER-001.
- **Obstacles** are objects above terrain, such as buildings, towers, and masts.
- **Restricted airspace** is a spatial, altitude, or time constraint on flight.

TER-001 must not parse obstacle or airspace KML as a terrain/DEM source. It may interoperate with a future common feasibility interface only through a separately approved task.

## Acceptance criteria

1. Flat terrain preserves the AGL relation and the approved no-terrain regression behavior.
2. Rising terrain increases absolute UAV altitude while AGL stays constant.
3. Falling terrain decreases absolute UAV altitude while AGL stays constant.
4. A deterministic hill profile follows `terrain + survey AGL`.
5. Sampling uses configurable spacing with a default near 25 m, including across multiple strip/leg boundaries; sample count scales with route length divided by step, not one query per metre.
6. Missing or non-finite elevation fails closed and never silently assumes zero.
7. Terrain-aware `precompute` changes time/energy where the supported three-dimensional path calculation changes them, while keeping seconds and watt-hours explicit.
8. A no-terrain input remains accepted and preserves the current flat calculation under the documented compatibility policy.
9. Existing constant-wind behavior and wind regression pass unchanged.
10. Existing flight-time/battery behavior and a configurable 10% terrain-policy landing reserve have deterministic regression coverage. The older 20% example is not the default.
11. Both solvers receive the same unchanged `pre` key names; `routes_raw` is unchanged.
12. Tests perform no network access and use only small deterministic fixtures.
13. If the approved implementation base contains an explicit UAV maximum-altitude field, terrain exceeding it is infeasible and has a deterministic test. Otherwise the limitation is documented, not filled with invented data.
14. No result claims certified safety or universal/global optimality beyond the existing exact-solver scope.
