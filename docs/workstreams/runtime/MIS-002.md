# MIS-002 — внешний перебор площадок и БВС

Адресат: агент Миши. Сначала прочитать `docs/architecture/OPTIMIZER_CORE.md`.

## Правила этого брифа

- Ветка от `main`. Контракт `v0`.
- Секреты, токены, адреса машин и URL с учётными данными не коммитить.
- Чужой шов не трогать: `geometry`, `precompute`, MILP, метаэвристика, `routes_raw`, `route_builder`, `validator`.
- Дедлайн показа: 25 сентября 2026, 21:00 Europe/Moscow.
- После показа код сшивает отдельная задача. Этот бриф сшивку не делает.

## Goal

Задание фиксирует зону, спектр, критерий и параметры оптимизации. Пользователь задаёт аэродромы координатами и борты карточками. На карточке — модель БВС, камера с ребром `compatibility` к этой модели, аэродром и количество. Список камер на форме спектр не фильтрует. В пул вызовов карточка попадает только если `required_spectrum` есть в `spectra` этой камеры. Каждый допущенный кандидат — один вызов ядра `run_core(InputData) -> dict` из протокола. Ядро вызывается как есть.

Зона на весь перебор одна. Пути `zone_constraints.kml_path` и `terrain.kml_path` фиксированы. Эти KML не парсить.

## Inputs and assumptions

- Протокол ядра: `docs/architecture/OPTIMIZER_CORE.md`.
- Один вызов по-прежнему содержит один `takeoff` и один объект `uav` с полем `count`.
- Из формы в конверт уходят зона (`area`), `required_spectrum`, `criterion` (`min_time` / `min_flight_hours`) и параметры оптимизации: лимит времени, ветер, общий профиль `gsd_cm_per_px`, `survey`, `power_coeffs`.
- Пользователь задаёт аэродромы, от 1 до 4: `id`, `lat`, `lon`. Идентификатор ставит система, вида `аэродром 1`. Первая строка по умолчанию `37.6000`, `55.7470`.
- Пользователь задаёт карточки бортов: `id`, `model_id`, `camera_id`, `aerodrome_id`, `count`. Идентификатор ставит система, вида `БВС 1`. Верхнего предела на число карточек нет. `uav.count` в вызове равен `count` карточки. Взлёт — координаты выбранного аэродрома.
- Поля `pads`, `required_camera` и `uav_types` не пишутся. Числа модели и камеры читаются из `src/planes/runtime/catalog/fleet_catalog.json`. Список камер на форме — рёбра `compatibility` выбранной модели. Спектр этот список не фильтрует.
- Кандидат — одна карточка борта. Сервер проверяет ребро модель–камера и что `required_spectrum` входит в `spectra` камеры. Порядок вызовов — порядок карточек.
- Карточка, у которой спектра нет в `spectra` камеры, не кандидат и `run()` не вызывает. Запись: id модели, id камеры, требуемый спектр, `spectra` камеры. Если ни одна карточка спектр не покрывает, исход `infeasible`, причина `no camera covers required spectrum`, даже если у части карточек ещё нет чисел.
- Пара, спектр которой совпал, но без всех пяти полей `_OPTICS`, либо без одного числа `airspeed_m_s`, `battery.energy_wh` и остальных полей `_FLIGHT`, в `run()` не идёт. Пропуск записывается: id модели, id камеры, каких полей нет. Пустые клетки не заполняются.
- Нет выполнимой карточки при покрытом спектре: ядро не вызывается, причина `no runnable board`. Камера без ребра к выбранной модели отклоняется. Конверт с `pads` или `uav_types` отклоняется.
- Рабочая гипотеза независимых вызовов действует только до показа 25 сентября. `count` карточки применяется к испытываемой модели целиком. Сравнение кандидатов читает расход, который ядро уже возвращает: `mission.uav_used`, время миссии, `routes[].energy_breakdown_wh`.

## Масштаб перебора

Перебор на этом показе допустим только в такой границе:

- зона одна, задана до перебора;
- спектр, критерий и параметры оптимизации фиксированы; форма камеры по спектру не прячет, пул вызовов берёт только покрытие `spectra`;
- аэродромов от 1 до 4;
- кандидат — одна карточка борта после проверки ребра, спектра и полноты листа;
- один кандидат — один вызов ядра;
- выполнимых карточек не больше 16; больше — явная ошибка, хвост не отбрасывается.

Внутри вызова остаются ограничения ядра, включая порог MILP `N≤3`, `M≤20`. Перебор эти пороги не сдвигает.

## Deliverables

1. Модуль перебора в `src/planes/runtime/enumeration/`. Он собирает `InputData` кандидата и вызывает чистую функцию ядра.
2. Фикстур пула в границе масштаба выше и детерминированный тест `tests/runtime/test_mis002*.py`.
3. На каждый успешный вызов сохранены `uav_used`, время и энергия из словаря `output.json`.
4. Строка статуса в `docs/status/runtime.md` со ссылкой на этот бриф.

## Acceptance criteria

- Число выполнимых вызовов не больше 16, аэродромов не больше 4. Свыше 16 — ошибка.
- Каждый вызов передаёт один `takeoff` и один `uav`. `uav.count` равен `count` карточки.
- KML зоны и KML местности не читаются этим модулем.
- Импортов, которые меняют `geometry`, `precompute` или солверы, нет.
- Одинаковые карточки, зона и seed дают одинаковый набор кандидатов и одинаковый порядок вызовов.
- Расход успешного вызова берётся из существующих полей протокола.

## Explicitly out of scope

- Перешивка VPS, `infra/**`, слушатель и деплой. `solver.solve` только выбирает внешний путь и пишет в ограничения id аэродрома, борта, модели и камеры.
- Сшивка вызовов в один план при общем пуле бортов и камер.
- Снятие приближений «один вылет», «постоянный ветер», «один GSD», «одинаковые борта внутри вызова».
- Правка MILP, метаэвристики, `route_builder`, `validator`, ключей `pre` и контракта `routes_raw`.

## Risks / decisions required

- Гипотеза независимых вызовов ломается, когда борта и камеры делятся между вылетами. Решение о сшивке здесь не принимается.
- Правило карточки — ребро `compatibility`, покрытие `required_spectrum` спектрами камеры и полнота чисел для текущего ядра, без новой оптической модели. Форма по-прежнему показывает все камеры модели. До ядра доходит выбранная пара только если её камера содержит спектр задания и лист чисел полон.
