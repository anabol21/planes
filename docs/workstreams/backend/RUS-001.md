## Live path on main

On `main` the live worker is `--engine runtime`. SQLite still stores the scenario unchanged; the listener applies the catalog. The API does not fill optics or power. The form sends `aerodromes` and `boards`, not `pads` or `uav_types`. See `docs/architecture/agent-brief-backend.md`. The goal below remains the original lifecycle prototype, whose CLI default is `fake`.

## Goal

Demonstrate the lifecycle `POST job → queued → running → terminal → result` without coupling the backend to the real optimizer or VPS implementation.

## Deliverable

1. Minimal API with `POST /jobs`, `GET /jobs/{id}`, and `GET /jobs/{id}/result`.
2. Input validation and immutable scenario snapshot.
3. SQLite-backed job store for the prototype.
4. Separate worker process with atomic job claim.
5. `OptimizationEngine` port and deterministic fake implementation.
6. Structured handling of completed, infeasible, failed, and timed-out outcomes.
7. Automated lifecycle test and one documented local run.

## Acceptance

- Heavy work is not executed inside the HTTP request.
- Concurrent workers cannot both claim the same queued job in the test scenario.
- Restart/error paths do not report false success.
- API payloads are versioned and match the committed fixtures.
- Swapping fake engine for the runtime adapter requires composition/configuration changes, not rewriting API or storage.

## Boundary

Backend owns job lifecycle and persistence. It does not implement routing/optimization and does not provision the VPS.
